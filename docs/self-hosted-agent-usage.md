# Agent usage (on-premises)

The Usage page displays token observations for each server agent, across its attached computers. It includes only observations the daemon could attribute to that agent; it does not import whole-machine or unrelated-session totals. These are operational measurements, not billing or audit records.

## Coverage

Collection begins after the updated server and computer daemon are running. Existing usage history is not backfilled. Turns before the first authenticated check-in create a durable missing-data warning rather than an attributed count. Every row is labelled partial: the daemon can miss observations before attachment, after a crash or during an outage that exceeds its local queue. A null value or an empty chart bucket means unavailable, not zero. A subtotal is the sum of the observations that are available for that metric, and may omit work; the UI shows the observation count for each metric. The record-level `complete` flag is reserved for a source that can prove it captured the entire turn. Current sources always set it to false; it does not claim coverage for a whole time range. Codex cached input is already included in the provider's input figure; it is split before storage. Claude's uncached, cache-read and cache-creation inputs are added once. Output includes reasoning, which is shown as a subset when reported.

OpenCode's shared-session event stream does not reliably identify which concurrent runner made a request. Until a per-request link is proven, the page records coverage as incomplete and leaves its counts unavailable; it does not attribute shared-session usage by timing. The same qualification applies to individual fields a runtime does not report. Unsupported runtimes produce computer-wide possible-gap warnings, which may also affect other agents placed on that computer.

## Collection and operation

Each computer authenticates to the server, binds the queue to its authenticated server and computer, and keeps pending observations in a private SQLite queue under its agent data directory. Successful delivery is acknowledged only after the server transaction commits; exact retries are idempotent. The queue is bounded at 10,000 observations. A full queue creates a durable computer-level warning if storage permits; a filesystem error can prevent even that warning. Before identity is known, a managed Computer stores only a warning, partitioned by the server identity supplied at launch so it survives credential rotation and cannot be sent to another server on the same origin. A legacy standalone daemon has no server identity before check-in; it partitions this warning by credential to avoid cross-server attribution, so rotating that credential before delivery leaves the warning in its old local queue. The page shows a warning for agents placed on a computer during a reported possible gap; the warning applies server-wide when the computer link or full placement interval cannot be established. It does not claim a particular agent lost data. Conflicting record IDs stay in a local quarantine for diagnosis. Records rejected because their agent placement is not yet established are set aside with a warning and retried periodically so other records can proceed. A future-timestamp record is also held and retried without an immediate gap. If it is still more than a day ahead on a repeated rejection, the daemon emits one possible-gap warning; an ordinary short clock delay does not leave a permanent warning. An attachment identity mismatch remains queued and requires investigation. Do not delete or edit a queue to conceal a gap.

The server checks the agent's recorded computer history, including migration quiescence and flip boundaries, before accepting new observations. The record's timestamp comes from the computer; skewed clocks or missing/inconsistent migration history can cause safe rejection. These checks prevent a different computer from reporting for an agent outside its known history; agents and the daemon running under the same OS user are not isolated from one another and a compromised computer can fabricate operational data.

The computer must be able to reach `/internal/computer/agent-usage/context` and `/internal/computer/agent-usage` with its existing computer credential. Follow the same gateway policy as the existing computer connection; do not create an unauthenticated public exception. Unsupported or disconnected computers continue operating normally but do not upload usage.

Before replacing any installed computer daemon, compare its version and capabilities with this source tree and account for its update mechanism. This checkout's daemon is older than the installed 1.0.64 computer binaries observed during development; building it unchanged would be a downgrade, and an updater could overwrite it. Resolve that compatibility and distribution question before rollout.

## Database upgrades

The on-prem migrations `0375_onprem_agent_usage`, `0376_onprem_agent_usage_placement` and `0377_onprem_agent_usage_received_index` add the usage tables, placement history and a reporting index. The placement migration locks the agents table while it snapshots current placements and installs tracking; the reporting index is built non-concurrently and can block writes to the usage table while it is built. Before any deployment, inspect the actual upstream and on-prem migration journals, resolve number/timestamp conflicts, rehearse the resulting migration sequence on a fresh copy of the current database, and take a verified backup. The migration timestamps are deliberately adjacent to the current on-prem predecessors but do not guarantee compatibility with a future upstream journal. During upgrades, also check the placement trigger against any upstream rename or removal of `agents.daemon_id`, `server_id`, or `deleted_at`. Update the computer daemon as well as the API and web app when rolling this out.
